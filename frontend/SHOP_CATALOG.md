## Ownership, placement, and backend boundary

Live purchases still call POST /api/shop/purchase and use the returned player. The backend rejects duplicate purchases and has a (user_id, item_id) primary key. New demo variant IDs are never sent to that endpoint.

Furniture Demo uses a separate initial 500-coin local purse and quantities keyed by variant ID. Purchases accept integer quantities 1–10, charge price × quantity, allow repeat purchases, and reject insufficient funds. Demo coins and quantities persist in per-player localStorage independently of player state. Existing one-copy saves migrate without resetting the balance.

Each placement has a UUID instanceId and variantId. Positions are keyed by instanceId. Backpack availability = owned quantity − placed instances. STORE removes only one instance and its position; ownership and coins stay unchanged. Starter objects keep their original IDs and are non-storable. Old item-keyed layouts migrate while retaining positions.

To support real quantity purchases later: add inventory quantities or owned instances to server storage and inventory responses; seed the new variant IDs; extend the purchase endpoint to validate quantity and charge the entire cost atomically; retain compatibility with existing one-copy purchases. No backend routes, schema, or shared Item/Player contract changed here.
